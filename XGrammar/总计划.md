## P0 ✅ 已完成 (2026-05-22) — 语法层关键缺失补全

### 背景

P0 前，代码框架已实现基本的 Token 级语法+语义检查流水线，但 lexer 和 GBNF 语法缺失比赛要求的下列语法元素：

- 访问修饰符 `public` / `private`
- 静态修饰符 `static`
- 构造器关键字 `init`
- 继承运算符 `<:`
- 类型参数 `<T, U>`（泛型）
- Lambda 参数类型标注 `x: Int32`
- Lambda body 为 block `{ => { ... } }`
- 接口抽象方法（无函数体的方法签名）
- 类的空 body 支持
- Field 的 `var`/`let` 前缀

这些缺失直接影响 **85%+ 的测试用例**（所有含泛型、类/接口、Lambda、修饰符的用例）。

### P0-1: 添加缺失的关键字（public/private/static/init）

**目标文件**: `src/lexer.py`

**问题分析**：lexer 已有 40 个关键字（`func`, `var`, `let`, `class` 等），但 `public`, `private`, `static`, `init` 不在关键字映射表中——它们被当作普通 `IDENTIFIER` token，导致 XGrammar 无法在 GBNF 规则中按关键字匹配。

**实现步骤**:

1. 在 `TokenType(Enum)` 类末尾（`KW_QUOTE` 之后）添加 4 个枚举值：
```python
KW_PUBLIC = auto()
KW_PRIVATE = auto()
KW_STATIC = auto()
KW_INIT = auto()
```
注意：`auto()` 生成的枚举值由 Python 自动分配，不影响已有 token ID 的顺序。

2. 在 `KEYWORDS` 字典末尾添加 4 个映射（在 `"quote"` 之后）：
```python
"public": TokenType.KW_PUBLIC,
"private": TokenType.KW_PRIVATE,
"static": TokenType.KW_STATIC,
"init": TokenType.KW_INIT,
```

3. 从 `CONTEXTUAL_KEYWORDS` 集合中移除 `"public"` 和 `"private"`（它们现在是硬关键字，不再是上下文关键字）。

**为什么不需要修改 TOKEN_SPECS**：关键字匹配依赖于 `_classify_identifier()` 方法——正则先匹配到 `IDENTIFIER`，然后查找 `KEYWORDS` 字典。如果命中，替换为对应的 `KW_*` TokenType。这是 lexer 的标准关键字处理流程，新增关键字自动享受此机制。

**语义影响**：将 `public`/`private` 从软关键字提升为硬关键字，意味着它们不能再作为变量名使用。这符合比赛语法子集的限定。

### P0-2: 添加 `<:` 继承运算符

**目标文件**: `src/lexer.py`, `src/token_vocab.py`

**问题分析**：仓颉（及比赛文档）使用 `<:` 表示类的继承/接口实现关系（如 `class Dog <: Animal`）。当前 lexer 将 `<:` 拆分为两个独立 token：`OP_LT`（`<`）和 `COLON`（`:`），而 GBNF 语法需要它作为一个整体 token 来解析继承关系。

**实现步骤**:

1. 在 `TokenType` 枚举的多字符运算符区域（`OP_LE` 之前）添加：
```python
OP_LT_COLON = auto()     # <:
```

2. 在 `TOKEN_SPECS` 列表的多字符运算符区域（`<=` 之前）添加正则：
```python
(r'<:', TokenType.OP_LT_COLON),
```
**关键**：必须放在 `<=` 之前！因为两者都以 `<` 开头，lexer 按 TOKEN_SPECS 顺序逐个尝试匹配。`<:` 放在 `<=` 之前可确保 `<:` 被正确匹配（`:` 和 `=` 是不同的第二个字符）。

3. 在 `src/token_vocab.py` 的 `TOKEN_TYPE_TO_VOCAB` 多字符运算符区域添加：
```python
TokenType.OP_LT_COLON: "LT_COLON",
```
`build_vocab_list()` 会自动发现所有 `OP_` 前缀的 token，无需手动添加。

**还顺便添加了 `!` 非空标记**：修改 `func_param` 规则为 `any_ident "NOT"? "COLON" type ...`，支持参数的非空标记（`x!: Int32`）。`!` 已作为 `OP_NOT` 存在于 lexer。

### P0-3: 类型列表 `&` 分隔符

**目标文件**: `grammar/cangjie_token.gbnf`

**修改**: `class_parents ::= "LT_COLON" type ("BIT_AND" type)*`

此前使用 `"COLON" type ("COMMA" type)*`（即 `: A, B`），改为 `<: A & B`。

### P0-4: GBNF 访问修饰符 + 静态修饰符

**目标文件**: `grammar/cangjie_token.gbnf`

**新增规则**（放在类型定义区域之后）:
```
access_modifier ::= "PUBLIC" | "PRIVATE"
static_modifier ::= "STATIC"
```

**修饰规则应用于以下声明**:
- `func_decl`: `access_modifier? static_modifier? "FUNC" ...`
- `method_def`: `access_modifier? static_modifier? "FUNC" ...`
- `constructor_def`: `access_modifier? "INIT" ...`（构造器不能是 static）
- `field_decl`: `access_modifier? static_modifier? ...`
- `class_decl`: `access_modifier? "CLASS" ...`
- `struct_decl`: `access_modifier? "STRUCT" ...`
- `interface_decl`: `access_modifier? "INTERFACE" ...`
- `enum_decl`: `access_modifier? "ENUM" ...`
- `extend_decl`: `access_modifier? "EXTEND" ...`

所有修饰符都是可选的（`?`），保持向后兼容。

### P0-5: 类型参数 `type_parameters`（泛型）

**目标文件**: `grammar/cangjie_token.gbnf`

**新增规则**:
```
type_param ::= any_ident
type_param_list ::= type_param ("COMMA" type_param)*
type_parameters ::= "LT" type_param_list "GT"
```

例如 `func identity <T, U>(...)` 中 `<T, U>` 对应的 token 序列是：`OP_LT IDENT(T) COMMA IDENT(U) OP_GT`

**应用的声明类型**:
| 声明 | 位置 | 说明 |
|------|------|------|
| `func_decl` | `"FUNC" any_ident type_parameters? "LPAREN"` | 泛型函数 |
| `method_def` | `"FUNC" any_ident type_parameters? "LPAREN"` | 泛型方法 |
| `class_decl` | `"CLASS" any_ident type_parameters? class_parents?` | 泛型类 |
| `struct_decl` | `"STRUCT" any_ident type_parameters? class_parents?` | 泛型结构体 |
| `interface_decl` | `"INTERFACE" any_ident type_parameters? class_parents?` | 泛型接口 |
| `interface_method` | `type_parameters? "FUNC" any_ident "LPAREN"` | 泛型抽象方法 |

**关键难点 — `<` 的歧义消解**:

`<` 在仓颉中有两种用途：
1. **类型参数**：`class Box <T>`、`func f <T>(x: T)`
2. **比较运算符**：`a < b`、`x < 10`

XGrammar 的 Earley PDA 通过**上下文自动消歧**：`type_parameters` 只在声明名之后的特定位置（紧跟标识符、在 `(` 或 `{` 或 `<:` 之前），而 `a < b` 出现在表达式上下文中。两者的语法路径不同，XGrammar 不会混淆。

已验证：`public class Box <T> { var value: T }` 和 `func identity <T>(x: T): T` 及 `var x = a < b` 均通过测试。

### P0-6: 构造器 `init`

**目标文件**: `grammar/cangjie_token.gbnf`

**新增规则**:
```
constructor_def ::= access_modifier? "INIT" "LPAREN" func_param_list? "RPAREN" block
```

**关键特性**:
- `init` 后面直接跟 `(` 和参数列表，没有函数名（与普通方法不同）
- 有 `block`（函数体），没有返回类型标注
- 只能在类体（`class_body`）内出现

**更新的类成员规则**:
```
class_member ::= field_decl | method_def | constructor_def
```

**语义层同步处理**（`src/semantic_checker.py`）:
- `KW_INIT` 加入 `_DECL_KEYWORDS`
- 处理时自动将 `_decl_name` 设为 `"init"`，`_decl_kw` 保持 `KW_INIT`
- 在 `_enter_brace` 中 `KW_INIT` 与 `KW_FUNC` 同等待遇（body 标记为 "func" scope）

### P0-8: Lambda 表达式完善

**目标文件**: `grammar/cangjie_token.gbnf`, `src/semantic_checker.py`

**比赛要求**:
```
lambda_expression = "{" [lambda_parameters] "=>" (expression | block_expression) "}"
lambda_param = identifier [":" type]
```

**P0 前的局限性**:
- lambda_param 只能是 `any_ident`，不支持类型标注
- body 只能是 `expression`，不支持 `block_expression`

**GBNF 修改**:
```
lambda_param ::= any_ident ("COLON" type)?
lambda_param_list ::= lambda_param ("COMMA" lambda_param)*
lambda_body ::= expression | block
lambda_expression ::= "LBRACE" lambda_param_list? "FAT_ARROW" lambda_body "RBRACE"
```

**语法歧义消解**:
Lambda `{ x => ... }` 和普通 block `{ ... }` 的区别在于 `=>` 的存在：
- `{` 后跟 `=>` → 无参 lambda
- `{` 后跟 `IDENT` 再跟 `=>` → 单参 lambda
- `{` 后跟 `IDENT` 再跟 `:` 再跟 `type` → 可能是 lambda typed param 或 struct field
- `{` 后跟 `IDENT` 再跟 `,` 再跟 `IDENT` → 多参 lambda

XGrammar 通过 `=>` 的存在来自动区分。`{ x => x + 1 }` 中的 `=>` 明确指示这是 lambda 而非表达式 block。

**语义层同步**:

| 新增状态 | 类型 | 作用 |
|---------|------|------|
| `_in_lambda_prefix` | `bool` | `{` 后、`=>` 前：标识符是参数名而非变量引用 |
| `_lambda_pending_params` | `List[(str, Optional[str])]` | 收集 lambda 参数名和可选类型 |
| `_entering_lambda_body` | `bool` | `=>` 后设置，下一个 `{` 标记为 func scope（支持 return） |

处理流程:
1. `{` → `_enter_brace`：若 tag=block 且非 struct init 且非 params 模式 → `_in_lambda_prefix = True`
2. `x` (IDENT) → `_handle_identifier`：`_in_lambda_prefix` 为 True → 收集到 `_lambda_pending_params`，不回查符号表
3. `:` (COLON) → 正常 advance
4. `Int32` (IDENT) → `_in_lambda_prefix` 为 True + prev=COLON → 更新上一条 pending param 的类型
5. `=>` (FAT_ARROW) → 将 `_lambda_pending_params` 注册到当前 scope，`_in_lambda_prefix = False`，`_entering_lambda_body = True`
6. `{` → `_enter_brace`：`_entering_lambda_body=True` → tag="func"，支持 return
7. `body` → 正常处理
8. `}` → `_exit_brace`：清除 lambda 状态

**1. `src/syntax_checker.py` — `_valid_after_kw_ident`**:

**2. `src/semantic_checker.py` — 修饰符路由**:

新增 `_MODIFIER_KEYWORDS` 集合（`KW_PUBLIC`, `KW_PRIVATE`, `KW_STATIC`），在 `process()` 中优先于 `_DECL_KEYWORDS` 处理——修饰符只做 `_advance()`，不启动声明状态机。

**3. `src/semantic_checker.py` — 类型参数语义**:

| 新增状态 | 类型 | 作用 |
|---------|------|------|
| `_in_type_params` | `bool` | 在 `<T, U>` 中 |
| `_pending_type_params` | `List[str]` | 收集类型参数名 |

处理流程:
- `OP_LT` 在声明上下文中（`_decl_kw` 为 FUNC/CLASS/STRUCT/ENUM/INTERFACE 且 `_decl_name` 已设置）→ `_in_type_params = True`
- `<` 到 `>` 之间的 `IDENTIFIER` → 收集到 `_pending_type_params`
- `OP_GT` → 将所有 `_pending_type_params` 注册到当前 scope（kind="class"，declared_type=自身名）
- 这些类型参数名随后可作为类型引用（在参数和返回值位置）

**4. `src/semantic_checker.py` — 继承类型引用**:

新增 `_in_inheritance` 标志，在 `<:` 后设置，在 `{` 进入 class body 时清除。在继承上下文中，标识符被当作类型引用而非变量查找。

**5. GBNF — 空 body 支持**:

将规则从 `"LBRACE" class_members "RBRACE"` 改为 `"LBRACE" class_members? "RBRACE"`。这允许空类、空接口、空 struct、空 block（`{ }`）。

XGrammar 不支持 `rule ::= ... |` 的空分支语法，因此采用在容器规则中使用 `?` 使整个成员列表可选的方式。

**6. GBNF — Field var/let**:

`field_decl ::= access_modifier? static_modifier? ("VAR" | "LET")? any_ident "COLON" type ("=" expression)? ";"?`

`var`/`let` 在字段声明中是可选的——仓颉类中 `x: Int64` 和 `var x: Int64` 都合法。

**7. GBNF — 顶层 var_decl 修饰符**:

`declaration` 规则中为 `var_decl` 添加 `access_modifier? static_modifier?` 前缀，支持 `private var x = 0` 这种顶层声明。

## P1 — 语义层增强（P1-1 ✅ P1-2 ✅ P1-3 ✅ P1-4 ✅ | P1-5~P1-6 待实现）

### P1-1: 运算符结果类型推导

**目标文件**: `src/semantic_checker.py`

**当前局限**：语义检查器追踪字面量类型和变量类型，但不对运算符表达式的结果类型做推导。例如 `a > b` 不会推导为 `Bool`，导致后续依赖该类型的检查（如 `func f(): Bool { return a > b }`）无法验证返回类型。

**实现方案 — 表达式类型栈**:

在 `SemanticChecker` 中维护一个**类型栈**（`_expr_type_stack: List[str]`），类似 JVM 操作数栈：

```
表达式处理流程（以 a + b * c 为例）：

Token:  a       +       b       *       c
类型栈: [Int64]  [Int64] [Int64, Int64] [Int64, Int64] → 归约

归约规则（当栈顶有足够操作数时触发）：
- 遇到二元运算符：弹出两个类型，查表得结果类型，压入
- 遇到一元运算符：弹出一个类型，查表得结果类型，压入
- 遇到字面量/变量：压入其类型
- 遇到 = ：左值类型 = 期望类型，右值类型栈归约后检查
```

**运算符类型规则表**:

| 运算符 | TokenTypes | 左操作数类型 | 右操作数类型 | 结果类型 |
|--------|-----------|-------------|-------------|---------|
| `+`, `-`, `*`, `/`, `%` | PLUS, MINUS, STAR, SLASH, PERCENT | Int | Int | Int |
| `+`, `-`, `*`, `/` | 同上 | Float | any | Float |
| `+`, `-`, `*`, `/` | 同上 | any | Float | Float |
| `==`, `!=`, `<`, `>`, `<=`, `>=` | EQ, NE, LT, GT, LE, GE | any num | any num | Bool |
| `&&`, `\|\|` | AND, OR | Bool | Bool | Bool |
| `!` | NOT | — | Bool | Bool |
| `&`, `\|`, `^` | BIT_AND, BIT_OR, BIT_XOR | Int | Int | Int |
| `<<`, `>>` | SHL, SHR | Int | Int | Int |
| `**` | POW | Int/Float | Int/Float | Int/Float |
| `..`, `..=` | RANGE, RANGE_INCL | Int | Int | Range\<Int\> |

**Int/Float 类型提升规则**:
- 两个 Int → 默认为 Int64（或保持较大者）
- 任一 Float → Float64（或保持较大者）
- `Int8 + Int16` → `Int16`（提升到较大）
- `Float32 + Float64` → `Float64`

**实现复杂度考虑**:

完全的类型栈实现需要处理括号、优先级、短路求值等，复杂度较高。**简化方案**：

由于比赛测试用例主要检查**赋值类型不匹配**（`var x: Int64 = "hello"`）和**返回类型不匹配**（`return x` 但 x 类型不对），可以采用**增量式二元追踪**替代完整栈：

1. 追踪当前连续的二元运算链
2. 在 `;` 或 `}` 等处触发类型兼容性检查
3. 仅对 `==`, `!=`, `<`, `>`, `<=`, `>=` 的结果类型推导为 Bool
4. 算术运算结果保持为数值类型（不追踪具体 Int/Float 精度差异）

这覆盖了绝大多数场景，且实现简单。

**修改文件清单**:
- `src/semantic_checker.py`:
  - 新增 `_expr_type_stack: List[str]`
  - 新增 `_is_comparison_result: bool`（标记最近一次比较运算）
  - 修改 `process()` 在运算符 token 时触发类型归约
  - 修改赋值/返回检查逻辑，使用归约后的类型

### P1-2: 函数调用实参类型检查

**目标文件**: `src/semantic_checker.py`

**当前局限**: 调用函数时（`f(args)`），语法检查通过，但**不校验实参类型是否与形参类型匹配**。例如 `func add(a: Int32, b: Int32)` 调用 `add("hello", true)` 不会被检测为错误。

**实现方案 — 调用栈式参数收集**:

```
调用分析流程（以 add(x + 1, y) 为例）：

Token:  add     (       x       +       1       ,       y       )
状态:   look-up 进入   类型栈  [Int64] [Int64, 归约  [Int64] [Int64, 收集第二个
               调用   [Int64]         Int64] →         String]  arg
                模式           Int64

在 ) 处触发类型检查:
  - 从符号表查找 add 的签名: (Int32, Int32) -> Int64
  - 收集的实参类型: [Int64, String]
  - 逐位对比: Int64 vs Int32 (compatible ✓), String vs Int32 (NOT compatible ✗)
  - 报错: "Argument 2 type mismatch: expected 'Int32', got 'String'"
```

**状态机设计**:

新增状态变量：
- `_in_call_args: bool` — 是否在函数调用的实参列表中
- `_call_func_name: Optional[str]` — 被调用的函数名
- `_call_arg_types: List[str]` — 已收集的实参类型
- `_call_paren_depth: int` — 调用入口的括号深度（处理嵌套调用）

状态转换：
1. IDENTIFIER (函数名) → 检查下一个 token 是否为 LPAREN（通过 `_prev_type` 判断）→ 设置 `_in_call_args = True`，记录函数名
2. LPAREN → 若 `_in_call_args`，记录 `_call_paren_depth = _paren_depth`
3. 在实参列表内：每个表达式的最终类型加入 `_call_arg_types`
4. COMMA → 重置当前实参类型追踪，开始收集下一个实参
5. RPAREN → 若 `_paren_depth == _call_paren_depth`（回到调用入口）→ 触发签名检查

**签名存储方案**:

当前符号表中函数存储为 `SymbolInfo(kind="function", declared_type=返回类型)`。需要扩展以存储参数签名：

```python
@dataclass
class SymbolInfo:
    name: str
    declared_type: Optional[str] = None  # 对于函数：返回类型
    kind: str = "variable"
    param_types: List[str] = field(default_factory=list)  # 新增：参数类型列表
    param_names: List[str] = field(default_factory=list)  # 新增：参数名列表
```

在注册函数声明时填充 `param_types` 和 `param_names`（从 `_pending_params` 获取）。

**嵌套调用处理**:

```cangjie
func f(x: Int64): Int64 { return g(h(x)); }
```
- `h(x)` 调用：进入实参模式，收集 x 的类型 Int64，匹配 h 签名 Int64→X，返回 X
- `g(...)` 调用：进入实参模式，实参类型为 h 的返回类型 X（从符号表查 g 的返回类型）

嵌套调用通过 `_call_paren_depth` 与 `_paren_depth` 的比较来区分层级。

**错误消息格式**:
```
"Argument 2 type mismatch in call to 'add': expected 'Int32', got 'String'"
"Too many arguments in call to 'f': expected 2, got 3"
"Too few arguments in call to 'f': expected 2, got 1"
```

### P1-3: Lambda 语义检查完善

**目标文件**: `src/semantic_checker.py`

**当前状态**: P0 已实现 Lambda 参数的基本语义处理（参数收集、注册到 scope、body 标记为 func），但仍有一个关键的**三歧义问题**：

**三歧义问题**: `{` 在仓颉中有三种可能的语义：

| 场景 | 示例 | 特征 |
|------|------|------|
| **Lambda** | `{ x => x + 1 }` 或 `{ x: Int32 => x + 1 }` | 在 `{` 和 `}` 之间有 `=>` |
| **普通 block** | `func f() { var x = 1; return x; }` | 以 statement 开头（`var`/`if`/`while`/`return`/`expression`） |
| **Struct 初始化** | `Point { x: 0.0, y: 0.0 }` | `{` 前是类型名，内部是 `field: value` 对 |

**当前检测逻辑**:

1. Struct init 检测：
```python
if (prev_type == IDENTIFIER          # 前一个是类型名
    and not in_params                # 不在参数列表中
    and decl_kw in (None, VAR, LET)  # 不在声明中
    and paren_depth == 0):           # 不在括号内
    self._in_struct_init = True
```

2. Lambda 检测：
```python
if (tag == "block"
    and not in_struct_init           # 不是 struct init
    and not in_params                # 不在参数列表中
    and decl_kw in (None, VAR, LET)):# 不在声明中或 var/let 的初始值
    self._in_lambda_prefix = True
```

**存在问题的场景**:

场景 A：`var f = { x + 1 }` — 这应该是一个返回 `x + 1` 的 block 表达式，不是 lambda（因为没有 `=>`）。当前代码会先设置 `_in_lambda_prefix = True`，然后在处理 `+` 时通过默认分支清除 lambda 模式（因为 `+` 不是允许的 lambda prefix token）。

场景 B：`Point { x: 0.0, y: 0.0 }` — strut init。`_prev_type == IDENTIFIER(Point)` 触发了 struct init 检测，正确。

场景 C：`{ x: 0.0, y: 0.0 }` — `_prev_type` 不是 IDENTIFIER（可能是 `=` 或 None），struct init 不触发，lambda prefix 触发。然后 `x: 0.0` 被当作 lambda 参数 `x` 带类型 `0.0`。但在 `=>` 或 `,` 出现之前，无法确定这真的是 lambda。

场景 D：`var f = { x: Int32 => x + 1 }` — 正确识别为 lambda。

**完善方案**:

1. **增强 Lambda 确认逻辑**：在当前 `_in_lambda_prefix = True` 的状态下，如果遇到非 lambda-prefix 允许的 token（如表达式运算符 `+`/`-`/`*`，或语句关键字 `var`/`if`/`while`/`return`），清除 lambda prefix 模式，回退为普通 block 表达式。

2. **Struct init 加强**：当 `_in_lambda_prefix = True` 且看到 `IDENT : literal` 模式时，延迟判断——直到看到 `=>` 或 `,` 才最终确认是 lambda 还是 struct init。如果在 `}` 之前没看到 `=>`，当作 struct init 处理。

3. **Lambda body 的类型检查**：
   - 若 body 是 expression → 检查 expression 类型是否符合上下文期望（如 `var f: (Int32) -> Int64 = { x => x + 1 }`）
   - 若 body 是 block → 检查 return 语句的类型

**修改清单**:
- `_handle_identifier`：在 lambda prefix 中遇到字面量（`0.0`）作为"类型"时，标记为可疑（可能是 struct init field value）
- `_exit_brace`：如果 scope 退出时 `_in_lambda_prefix` 仍为 True → 不是 lambda，清理 pending params
- 处理 `var f = { x: Int32 => x + 1 }` 中 `var f` 的类型推断

### P1-4: 泛型类型参数推导（最难的 15% 用例）

**目标文件**: `src/semantic_checker.py`

**比赛要求**: 15% 测试用例包含 Lambda 且泛型类型参数**可省略**（需类型推导）。

**问题描述**:

```cangjie
// 显式泛型（85% 用例）
func identity <T>(x: T): T { return x }
var a: Int64 = identity <Int64> (42)

// 隐式泛型（15% 用例 — 省略类型参数，需推导）
var b = identity(42)       // 推导 T = Int64
var c = identity("hello")  // 推导 T = String
```

当 `identity(42)` 中省略了 `<Int64>`，语义检查器需要：
1. 识别这是一个泛型函数调用（函数签名中有类型参数）
2. 从实参 `42` 的类型（Int64）推导出 `T = Int64`
3. 推导函数的返回类型为 `Int64`
4. 继续检查后续的类型兼容性

**推导算法 — 约束求解**:

```
输入: 泛型函数签名 func f<T1, T2, ...>(p1: A1, p2: A2, ...): R
      调用实参类型 actual_1, actual_2, ...

算法:
1. 建立类型参数集合 {T1, T2, ...}
2. 对每个形参 pi: Ai:
   a. 若 Ai 是具体类型（如 Int64）:
      检查 actual_i 是否与 Ai 兼容 → 是/否
   b. 若 Ai 是类型参数（如 T1）:
      添加约束 T1 = actual_i
   c. 若 Ai 是泛型类型（如 Array<T1>）:
      从 actual_i（如 Array<Int64>）匹配出 T1 = Int64
3. 检查约束一致性：同一类型参数不能有两个冲突的约束
4. 代入推导结果到返回类型 R，得到具体返回类型
```

**示例推导**:

```
func identity<T>(x: T): T { return x }

调用 identity(42):
  - 实参类型: Int64
  - 形参 x: T → 约束 T = Int64
  - 返回类型 T → 代入 T=Int64 → 返回类型 = Int64
  - ✓ 无冲突

调用 identity("hello"):
  - 实参类型: String
  - 形参 x: T → 约束 T = String  
  - 返回类型 T → 返回类型 = String
  - ✓ 无冲突

func pair<T, U>(first: T, second: U): Array<T> { ... }
调用 pair(42, "hello"):
  - first: T = Int64
  - second: U = String
  - 返回: Array<T> = Array<Int64>
  - ✓ 无冲突

调用 pair(42, 100):
  - first: T = Int64
  - second: U = Int64  (≠ T 的约束，但 U 是独立参数)
  - ✓ 无冲突
```

**实现要点**:

1. **符号表扩展**: `SymbolInfo` 新增 `type_params: List[str]` 字段，记录泛型函数的类型参数列表。

2. **调用时推导**: 在 `P1-2`（实参类型检查）的基础上，当函数有类型参数且调用未显式标注时，触发推导：
```python
def _infer_type_params(func_sym, arg_types):
    """从实参类型推导类型参数。返回 {T1: Type1, T2: Type2, ...}"""
    constraints = {}
    for (param_name, param_type), actual_type in zip(func_sym.param_info, arg_types):
        if param_type in func_sym.type_params:
            # 参数类型就是类型参数本身
            constraints[param_type] = actual_type
        elif is_generic_type(param_type):
            # 参数是泛型类型如 Array<T>
            match_generic(param_type, actual_type, constraints)
    return constraints
```

3. **结果类型替换**: 推导完成后，将函数返回类型中的类型参数替换为具体类型，以便后续的赋值/返回类型检查。

**难点**: 
- 嵌套泛型 `Array<Array<T>>` 的匹配
- 多个类型参数的约束一致性验证
- 泛型方法（类中的泛型方法）的类型参数推导

## P2 — 性能优化与工程完善

### P2-1: 语义检查器性能优化

**目标**: 从 21.6 μs/token 优化到 15–20 μs/token

**当前瓶颈分析**:

`process()` 方法使用 if-elif 链（约 20 个分支）对每种 token 类型做路由。每次 token 都要经过约 10–15 次条件判断才能到达正确的分支。

**优化策略**:

1. **字典分发替代 if-elif 链**（最大收益）:
```python
# 旧: 长 if-elif 链
if tt == TokenType.LBRACE:
    ...
elif tt == TokenType.RBRACE:
    ...
# ...

# 新: 字典查找 O(1)
_HANDLERS: dict[TokenType, callable] = {
    TokenType.LBRACE: '_handle_lbrace',
    TokenType.RBRACE: '_handle_rbrace',
    # ...
}

def process(self, token):
    handler = _HANDLERS.get(token.type)
    if handler:
        return handler(self, token)
    else:
        return self._handle_default(token)
```
预期收益：~30–40% 减少条件判断开销。

2. **frozenset 查找优化**:
`_STATEMENT_START_TOKENS` 等集合成员检查是 `if tt in frozenset`。可以用 `dict` 替代：
```python
# frozenset 查找: O(len(set)) 但集合哈希计算有开销
# 替代: 直接在 dict 中查，TokenType → bool
_STATEMENT_START: dict[TokenType, bool] = {t: True for t in [...]}
# 使用: if _STATEMENT_START.get(tt)
```

3. **预计算 `_BUILTIN_NAMES` 的类型映射**:
```python
# 预计算: {"Int32": "Int32", "Float64": "Float64", ...}
_BUILTIN_TYPES: dict[str, str] = {t: t for t in _BUILTIN_NAMES if t in _NUMERIC_TYPES or t in ("String", "Bool", "Rune")}
```
避免每次 `_lookup_identifier` 都做字符串比较 + 集合检查。

4. **属性访问缓存**:
将 `token.type`、`token.text` 等频繁访问的属性缓存到局部变量（已在 process 开头做了 `tt = token.type`，但 handler 方法仍可能重复访问）。

5. **Python `__slots__`**:
为 `SymbolInfo`、`SemanticResult`、`Token` 等 dataclass 添加 `__slots__`，减少每个对象的内存开销和属性访问时间。

**性能测试方法**:


## P1-4 实现总结 ✅ (2026-05-24)

**目标**：泛型类型参数推导 — 支持 `identity(42)` 这类省略显式泛型实参的函数调用，从实参类型推导 `T = Int64` 并同步推导返回类型。

**实现方式**：函数符号保存泛型形参 + 调用闭合时求解类型参数约束。

**修改 `src/semantic_checker.py`**：
1. `SymbolInfo` dataclass 新增 `type_params: List[str]` 字段，用于保存函数声明中的泛型形参列表。
2. `SemanticChecker.__init__` 新增 `_last_call_return_type: Optional[str]`，在一次函数调用检查后保存推导出的返回类型。
3. `process()` 的 `OP_GT` 分支：当处于函数声明的类型参数列表时，将 `_pending_type_params` 写入当前函数符号的 `type_params`，例如 `func identity<T>` 记录为 `["T"]`；非函数声明仍保留原有作用域可见行为。
4. `process()` 的函数调用 `RPAREN` 分支：优先使用 `_last_call_return_type` 更新 `_current_expr_type`，使 `var a: Int64 = identity(42)` 能在赋值检查阶段看到真实返回类型 `Int64`。
5. `_check_call_args()` 扩展为泛型约束求解：
   - 对形参类型为类型参数的情况建立绑定，如 `T -> Int64`。
   - 同一类型参数重复出现时校验一致性，如 `same(1, "x")` 报错。
   - 普通形参继续使用 `_are_types_compatible()` 校验，如 `count: Int64` 不能接收 `String`。
   - 返回类型为类型参数时替换为推导出的具体类型；无法推导则返回语义错误。

**修改 `main.py`**：
1. 新增 5 个 P1-4 正例：`identity(42)` 推导 `Int64`、`identity("hello")` 推导 `String`、`second(1, "ok")` 推导多类型参数、`first(1, "ok")` 验证返回类型可来自非最后实参、`same(1, 2)` 校验重复泛型参数一致。
2. 新增 4 个 P1-4 反例：`identity(42)` 赋给 `String`、`same(1, "x")`、`first(1, "ok")` 赋给 `String`、`take("x", "bad")`。

## P1-3 实现总结 ✅ (2026-05-24)

**目标**：Lambda 语义检查完善 — 解决 `{` 的三歧义问题（Lambda / block 表达式 / struct init）

**核心问题**：
- `<br>` 在仓颉中有三种语义：Lambda（`{ x => x + 1 }`）、block 表达式（`{ x + 1 }`）、struct init（`Point { x: 0.0 }`）
- 语法层：`primary` 规则缺 `block`，导致 `{ x + 1 }` 作为表达式被语法拒绝（只能走 lambda_expression 路径）
- 语义层：lambda prefix 模式下收集的标识符（潜在参数名），在模式被推翻时未做作用域查找验证

**修改 `grammar/cangjie_token.gbnf`**：
1. `primary` 规则新增 `| block` 分支 — 允许 block 表达式出现在表达式位置（如 `var r = { x + 1 }`）
   - XGrammar Earley PDA 自动并行探索 lambda_expression 和 block 两条路径，通过后续 token 消歧

**修改 `src/semantic_checker.py`**：
1. 新增 `_LAMBDA_PREFIX_VALID_TOKENS` 常量 — 定义 lambda 参数列表中合法的 token 类型集合：
   - `IDENTIFIER`（参数名/类型名）、`COLON`（类型标注）、`COMMA`（多参数）、`OP_FAT_ARROW`（确认 lambda）、`OP_DOT`（点号类型名如 `module.Type`）、`RBRACE`（由 `_exit_brace` 处理）
2. `process()` 顶部新增 lambda prefix 展开检查（在 token 特定处理之前）：
   - 若 `_in_lambda_prefix = True` 且当前 token 不在 `_LAMBDA_PREFIX_VALID_TOKENS` 中 → 调用 `_unwind_lambda_prefix()` 验证已收集的标识符
   - 展开后当前 token 正常传递给对应 handler（如 `+` 传给算术运算符 handler）
3. 新增 `_unwind_lambda_prefix()` 方法：
   - 遍历 `_lambda_pending_params`，对每个收集的标识符做作用域查找
   - 若未定义且非内置名 → 返回 `Undefined variable` 错误
   - 若已定义 → 将其类型设为 `_current_expr_type`（延续表达式类型追踪）
   - 若全部合法 → 返回 None（调用者继续正常处理当前 token）
4. `_exit_brace()` lambda 未确认时的验证：
   - 当 `}` 闭合时 `_in_lambda_prefix` 仍为 True（全程未看到 `=>`）→ 对收集的标识符做作用域查找
   - 若任何标识符未定义 → 返回错误（block 表达式引用了未定义变量）
5. `_enter_brace()` 支持嵌套 lambda 检测：
   - 新增 `entered_lambda_body` 局部变量，保存 `_entering_lambda_body` 的值
   - `allow_lambda` 条件扩展：`tag == "block"` 或 `(tag == "func" and entered_lambda_body)`
   - 使嵌套 lambda（如 `{ x: Int32 => { y: Int32 => x + y } }`）的内层 `{` 正确触发 lambda prefix 检测
6. 移除默认 handler 中冗余的 lambda 展开逻辑（已提升到 `process()` 顶部统一处理）

**测试验证**：
- 10 个 P1-3 专项测试全部通过：
  - 正例：typed param lambda、untyped param lambda、no-param lambda、block body lambda、block 表达式（已定义变量）、嵌套 lambda、多参数 lambda、lambda 立即调用
  - 反例：block 表达式未定义变量、嵌套 block 未定义变量、lambda body 引用未定义变量
- 15 个原始回归测试无退化
- 20 个 P0 功能测试全部通过

## P1-1 实现总结 ✅ (2026-05-23)

**目标**：运算符结果类型推导 — 比较/逻辑运算符产生 Bool 类型

**实现方式**：增量式二元追踪（简化方案）

**修改 `src/semantic_checker.py`**：
1. 新增 `_expr_has_comparison: bool` 标志 — 追踪当前表达式是否包含比较/逻辑运算
2. 新增 `_prev_text: str` — 追踪前一 token 文本（供 P1-2 函数调用检测复用）
3. `_advance()` 新增 `text` 参数，同步更新 `_prev_text`
4. `process()` 新增运算符分类处理：
   - 比较运算符（`==`, `!=`, `<`, `>`, `<=`, `>=`）→ `_expr_has_comparison = True`
   - 逻辑运算符（`&&`, `||`）→ 同上
   - 算术运算符（`+`, `-`, `*`, `/`, `%` 等）→ 保持数值类型不变
   - `OP_LT` / `OP_GT`：在非 `_in_type_params` 上下文中视为比较运算符
5. `_resolve_expr_type()` 辅助方法：若 `_expr_has_comparison` 为 True，返回 `"Bool"`
6. 所有类型检查点（STATEMENT_START_TOKENS、SEMICOLON、`_check_assignment_type`、`finalize`）统一使用 `_resolve_expr_type()`
7. 表达式边界（`;`、`}`、`,`、`)`）清除 `_expr_has_comparison`

**新增常量**：`_COMPARISON_OPS`、`_LOGICAL_OPS`、`_ARITHMETIC_OPS`

## P1-2 实现总结 ✅ (2026-05-23)

**目标**：函数调用实参类型检查 — 验证调用实参与形参类型匹配

**实现方式**：调用栈式参数收集 + 签名比对

**修改 `src/semantic_checker.py`**：
1. `SymbolInfo` dataclass：新增 `param_types: List[str]` 和 `param_names: List[str]` 字段
2. `SemanticChecker.__init__`：新增调用追踪状态
   - `_func_decl_name: Optional[str]` — 函数声明名（不被参数名覆盖）
   - `_in_call_args: bool` — 是否在函数调用实参列表中
   - `_call_func_name: Optional[str]` — 被调用函数名
   - `_call_arg_types: List[str]` — 已收集的实参类型列表
   - `_call_paren_depth: int` — 调用入口的括号深度（处理嵌套调用）
3. `_register_declaration()`：保存 `_func_decl_name = text`
4. `_enter_brace()`：用 `_func_decl_name` 查找函数符号，保存 `param_types` 和 `param_names`
5. `process()` LPAREN 分支：检测 `IDENTIFIER` + `LPAREN` 模式 → 进入调用实参模式
6. `process()` COMMA 分支：在实参模式中收集当前表达式类型到 `_call_arg_types`
7. `process()` RPAREN 分支：在调用深度闭合时触发签名检查，并将函数返回类型设为 `_current_expr_type`（支持嵌套调用）
8. `_check_call_args()` 新增方法：
   - 参数数量检查 → `"Argument count mismatch..."`
   - 逐参数类型兼容性检查 → `"Argument N type mismatch..."`
   - 使用 `_are_types_compatible()` 做类型兼容判断
9. `_end_decl()`：清除 `_func_decl_name`

**测试验证**：13 个专项测试全部通过（包含有效调用、类型不匹配、参数数量错误、嵌套调用、表达式实参、递归调用等场景），所有回归测试无退化
