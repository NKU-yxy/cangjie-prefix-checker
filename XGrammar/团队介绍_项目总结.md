# 仓颉语法+语义检查器 — 给队员看的项目介绍

## 一、我们做了什么？

简单说：我们做了一个**仓颉代码的"拼写检查器"**。

就像你用 Word 打字时，拼错的单词下面会有红色波浪线一样——我们这个东西，你给它一段仓颉代码，它能**一个 token 一个 token 地告诉你**：这个对不对？错在哪？

而且我们有**两种检查同时进行**：
- **语法检查**：这个 token 放在这个位置，语法规则允许吗？（比如 `var = 42` 不行，因为 `var` 后面必须跟一个变量名）
- **语义检查**：语法上没问题，但意思对吗？（比如你声明了 `Int32` 类型的变量，却塞了个字符串进去，那就不行）

**关键设计**：遇到第一个错误就停，不浪费时间继续往后检查。因为我们追求的是**速度**。

---

## 二、为什么这么做？跟原来比快了多少？

原本的方案是"字符级"检查：把代码一个字符一个字符地喂给一个叫 Earley PDA 的算法，每喂一个字符都要跑一轮循环，所以慢。

我们改成了"Token 级"：先把代码切成一个个有意义的词（token），然后对每个 token 做一次 O(1) 的查表操作——就像查字典，翻到那一页看一眼就行，不用从头翻到尾。

**速度对比（拿一个 346 行、1772 个 token 的仓颉代码测试）：**

| 方案 | 耗时 | 说明 |
|------|------|------|
| 老方案（字符级） | ~785 毫秒 | 一个字符一个字符地检查 |
| 新方案（Token 级） | ~47 毫秒 | 一个 token 一个 token 查表 |
| **快了** | **约 17 倍** | |

换算一下：**每检查一个 token 只需要 26 微秒**（1 微秒 = 百万分之一秒）。如果一段代码有 500 个 token，我们预估只需要 **13 毫秒**就能检查完（目标是不超过 50 毫秒，我们做到了）。

## 三、整个流程是怎么跑的？（给小白讲版）

想象你是一个老师，拿着一张"仓颉语法规则表"和一本"学生名册"，学生交上来一段代码，你要逐行检查。我们程序做的事跟你一模一样：

### 第 1 步：分词（Lexer 词法分析器）

把源代码切成一个个小块，每个小块叫一个 **token**。

比如 `var x = 42` 会被切成：
```
var     → 关键字（KW_VAR）
x       → 标识符（IDENT）
=       → 赋值号（OP_ASSIGN）
42      → 整数（INT_LIT）
```

这一步由 `src/lexer.py` 完成，它认识 114 种不同的 token 类型（关键字、运算符、分隔符、各种字面量等等）。

### 第 2 步：Token → 数字编号（Token 词汇表）

语法检查器（XGrammar）不认字符串，只认数字编号。所以我们需要一本"翻译词典"，把每种 token 类型映射成一个数字 ID。

```
KW_VAR  → 0
IDENT   → 25
OP_ASSIGN → 50
INT_LIT → 75
...
```

这一步由 `src/token_vocab.py` 完成，一共 111 个词条。

### 第 3 步：语法检查（Syntax Checker）

这是我们自己写的 GBNF 语法规则文件（`grammar/cangjie_token.gbnf`，269 行），描述了仓颉语言所有合法的 token 排列方式。

比如规则里有一条：
```
var_decl ::= ("VAR" | "LET") IDENT (":" type)? ("=" expression)? ";"?
```

意思是：一个变量声明，必须以 `var` 或 `let` 开头，后面跟一个标识符，然后可以有一个类型注解（`: Int32`），可以有一个初始值（`= 42`），最后可以有一个分号。

程序拿到 token 序列后，一个接一个地问 XGrammar："第 1 个 token 合法吗？第 2 个呢？第 3 个呢？" XGrammar 内部用了一个叫 **bitmask（位掩码）** 的数据结构，查表 O(1)，极快。

### 第 4 步：语义检查（Semantic Checker）

语法检查说"句子结构没问题"，语义检查接着说"意思对不对"。

由 `src/semantic_checker.py` 完成（672 行），主要做三件事：

#### a) 符号表（变量名册）

程序维护一个**栈**（叠盘子结构），每遇到一个 `{` 就往顶上放一个新盘子，每遇到一个 `}` 就从顶上拿掉一个盘子。每个盘子里记录着**在当前大括号范围内声明的所有变量和函数**。

当你使用一个变量 `x` 时，程序从最顶上的盘子开始往下找，第一个找到的就是当前有效的 `x`。

```
func f() {          ← 放盘子 1（全局）
    var x = 1;      ← 在盘子 1 上记下: x → Int64
    {               ← 放盘子 2
        var x = 2;  ← 在盘子 2 上记下: x → Int64（遮蔽了盘子 1 的 x）
        print(x);   ← 从盘子 2 找到 x → 2 ✓
    }               ← 拿掉盘子 2
    print(x);       ← 从盘子 1 找到 x → 1 ✓
}
```

#### b) 类型检查

每个变量声明的类型和每个字面量的类型都会被记录下来。当赋值或返回时，检查两边类型是否匹配。

比如：
```
let a: Int32 = "hello";   ← 报错！Int32 不能装字符串
```

支持简单的类型兼容：整数可以自动提升为浮点数（`Int32 → Float64` 是 OK 的）。

#### c) 上下文约束

一些语句只能在特定位置出现：
- `break` 和 `continue` 必须在循环（while/for）里面
- `return` 必须在函数里面
- `main()` 函数最多只能有一个

### 第 5 步：输出结果

最终输出两行数字：
```
token: main ( ) { let a : Int64 = "hello" }
语法:  1,   1, 1, 1,  1, 1, 1,    1, 1
语义:  1,   1, 1, 1,  1, 1, 1,    1, 0
                                           ↑ 这里语义报错
```

1 表示通过，0 表示失败。遇到第一个 0 就停，后面不查了。

## 五、还没做 / 有局限的地方

### 1. 运算符结果类型不会推导

比如 `a > b`（a 和 b 都是 Float64），结果应该是 Bool。但我们现在不推导这个，所以：

```cangjie
func f(): Bool {
    return 1 > 2;  // 不会报错（但其实应该能自动判断出 Bool）
}
```

**影响**：不会误判（不会把正确代码标成错误），但会漏掉一部分真正的类型错误。

### 2. 泛型类型在表达式里不能用

`var x: Array<Int32>` 这种写在类型位置的没问题。

但是 `var x = Array<Int32>()` 这种在表达式位置构造泛型对象的，语法不支持。

### 3. 函数调用参数不检查

```cangjie
func add(a: Int32, b: Int32): Int32 { return a + b; }
add("hello", true);  // 不会报错（传错类型了但没检查）
```

### 4. 隐式 main() 重复检测有 bug

用 `func main()` 写重复了能检测，但直接写 `main() {}`（不带 func 关键字）的，第二次重复检测不出来。

### 5. 不支持嵌套函数

函数里不能再定义函数（这是仓颉语法规则本身就这样的，不是我们的 bug）。

### 6. 类型检查有时依赖分号

如果漏写分号，偶尔会出现类型状态没清干净的情况。不过我们的测试代码里都加了分号，所以目前不影响。
