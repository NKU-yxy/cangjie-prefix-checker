## 1. 整体架构

```
┌──────────────────────────────────────────────────────────────────┐
│                         main.py (CLI 入口)                        │
│                 解析命令行参数 → 调用 check_cangjie()               │
└────────────────────────────┬─────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│                   syntax_checker.py (统一调度层)                   │
│                                                                   │
│  CangjieSyntaxChecker.check_token_by_token(code)                  │
│                                                                   │
│  1. 预处理注释 → 2. 调 lexer 分词 → 3. 过滤空白 token              │
│  4. 逐个 token:                                                   │
│     ├─ matcher.accept_token(token_id) → 语法是否合法?             │
│     ├─ semantic.process(token)        → 语义是否合法?             │
│     └─ 任一失败 → 立即返回 CheckResult(1/0 列表 + 错误信息)        │
│  5. 调用 semantic.finalize() → 检查末尾残留的类型不匹配             │
│  6. 返回 CheckResult                                              │
└───────┬───────────────────────┬──────────────────────────────────┘
        │                       │
        ▼                       ▼
┌──────────────────┐   ┌──────────────────────────────┐
│    lexer.py       │   │   semantic_checker.py         │
│                   │   │                               │
│  CangjieLexer     │   │  SemanticChecker              │
│  ├─ TokenType     │   │  ├─ ScopeStack (栈式符号表)     │
│  ├─ Token         │   │  ├─ 类型追踪 (_current/       │
│  ├─ KEYWORDS      │   │  │   _expected/_func_return) │
│  └─ tokenize()    │   │  ├─ 上下文约束 (break/        │
│                   │   │  │   continue/return 位置)    │
│                   │   │  └─ process(token) →          │
│                   │   │     SemanticResult            │
└──────────────────┘   └──────────────────────────────┘
        │
        ▼
┌──────────────────┐
│  token_vocab.py   │
│                   │
│  TokenType → ID   │
│  ├─ TOKEN_ID_MAP  │
│  ├─ TOKENIZER_INFO│
│  └─ get_token_id()│
└──────────────────┘
```

**关键依赖关系：**

| 模块 | 依赖 | 说明 |
|------|------|------|
| `main.py` | `syntax_checker.py` | 调用 `check_cangjie()` |
| `syntax_checker.py` | `lexer.py`, `token_vocab.py`, `semantic_checker.py`, `xgrammar` | 统一调度层，组装所有模块 |

| `lexer.py` | 无外部依赖 (仅 re, dataclasses) | 独立词法分析 |

## 2. 数据流全貌

```
输入: 一段仓颉源代码 (字符串)
      │
      ▼
┌──────────────────────────────────────┐
│ 步骤1: 注释预处理                      │
│ CangjieSyntaxChecker._preprocess_     │
│ comments(code)                        │
│ ── 去除 // 行注释 和 /* */ 块注释       │
│ 输出: 纯净的仓颉代码 (字符串)           │
└────────────────┬─────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────┐
│ 步骤2: 词法分析 (Lex)                  │
│ CangjieLexer(source).tokenize()       │
│ ── 正则逐条匹配，233 条规则             │
│ ── 标识符自动区分关键字/普通标识符        │
│ ── 特殊处理: 字符串、字符、多行字符串      │
│ 输出: List[Token]                     │
│   每个 Token = {type, text, line, col}│
└────────────────┬─────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────┐
│ 步骤3: 过滤                             │
│ 去掉: WS, NEWLINE, COMMENT, UNKNOWN   │
│ 输出: 有效 Token 列表 (significant)     │
└────────────────┬─────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────┐
│ 步骤4: 逐 Token 检查 (循环)            │
│                                       │
│  for each token in significant:       │
│    token_id = get_token_id(token.type)│
│                                       │
│    ┌─ 语法检查 ────────────────────┐  │
│    │ matcher.accept_token(id)      │  │
│    │   ├─ True  → continue         │  │
│    │   └─ False → 返回错误 (语法)   │  │
│    │                               │  │
│    │ 辅助检查:                      │  │
│    │ _token_invalid_in_kw_context  │  │
│    │   检查 var x + 这种非法组合     │  │
│    └───────────────────────────────┘  │
│                                       │
│    ┌─ 语义检查 ────────────────────┐  │
│    │ semantic.process(token)       │  │
│    │   ├─ 更新作用域 (push/pop)     │  │
│    │   ├─ 注册声明/查找引用          │  │
│    │   ├─ 追踪表达式类型             │  │
│    │   ├─ 检查 break/continue/     │  │
│    │   │   return 位置合法性        │  │
│    │   └─ 返回 SemanticResult      │  │
│    └───────────────────────────────┘  │
│                                       │
│    任一失败 → 停止循环，返回结果        │
└────────────────┬─────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────┐
│ 步骤5: 收尾检查                        │
│ semantic.finalize()                   │
│ ── 检查末尾是否有残留的类型不匹配        │
└────────────────┬─────────────────────┘
                 │
                 ▼
输出: CheckResult {
    tokens:          ["var", "x", "=", "42"]
    syntax_results:  [1,     1,   1,   1  ]
    semantic_results:[1,     1,   1,   1  ]
    passed:          true
    error_*:         ...                  (仅失败时有)
}
```

## 3. 模块详解

### 3.1 lexer.py — 词法分析器

**文件**: `src/lexer.py` (567 行)  
**职责**: 把源字符串切成 Token 序列  
**无外部依赖**: 纯 Python 实现

#### 核心类: TokenType (Enum, 114 个枚举值)

```
TokenType
├── 关键字 (40个): KW_FUNC, KW_VAR, KW_LET, KW_IF, KW_ELSE, KW_WHILE, ... 
├── 字面量 (6个):  IDENTIFIER, INTEGER_LITERAL, FLOAT_LITERAL, STRING_LITERAL, ...
├── 多字符运算符 (36个): OP_EQ(==), OP_NE(!=), OP_AND(&&), OP_ARROW(->), ...
├── 单字符运算符 (17个): OP_PLUS, OP_MINUS, OP_STAR, OP_ASSIGN, ...
├── 分隔符 (10个): LPAREN, RPAREN, LBRACE, RBRACE, SEMICOLON, COLON, ...
└── 特殊 (5个):     WS, NEWLINE, COMMENT_LINE, COMMENT_BLOCK, EOF, UNKNOWN
```

#### 核心类: Token (dataclass)

```python
@dataclass
class Token:
    type: TokenType    # 如 TokenType.KW_VAR
    text: str          # 原始文本, 如 "var"
    line: int          # 行号 (从1开始)
    column: int        # 列号 (从1开始)
```

#### 核心类: CangjieLexer

```
CangjieLexer(source, skip_ws=True, skip_comments=True)
├── _pos, _line, _col    : 内部扫描状态
├── tokenize()           : 返回完整 Token 列表
├── tokenize_with_str_context() : 返回 (Token, start, end) 列表
└── _generate()          : 生成器, 逐个 yield Token

匹配策略: TOKEN_SPECS 数组按优先级排列 (共 233 条正则)
  1. 先匹配多字符运算符 (如 ==, != 优先于 =, !)
  2. 再匹配字面量 (浮点数优先于整数)
  3. 最后匹配单字符
  4. 兜底: . 匹配任意单字符 → UNKNOWN

特殊扫描器:
  ├── _scan_string()     : 处理 "..." 字符串, 支持转义
  ├── _scan_rune()       : 处理 r'x' 字符字面量
  └── _scan_block_comment(): 处理 /* */ 嵌套注释

关键词区分: _classify_identifier()
  当正则匹配到 IDENTIFIER 后, 查 KEYWORDS 字典:
    是关键字 → 改用对应的 KW_XXX TokenType
    不是     → 保持 IDENTIFIER
```

**关键常量:**

| 常量 | 说明 | 示例 |
|------|------|------|
| `KEYWORDS` (dict) | 字符串 → TokenType | `"func" → KW_FUNC` |
| `CONTEXTUAL_KEYWORDS` (set) | 上下文关键字 (目前仅记录, 未使用) | `"abstract"`, `"public"` |
| `PRIMITIVE_TYPES` (set) | 原始类型名 (词法上仍是 IDENT) | `"Int32"`, `"Float64"`, `"String"` |

### 3.2 token_vocab.py — Token 词汇表

**文件**: `src/token_vocab.py` (236 行)  
**职责**: 把 TokenType 映射为 XGrammar 能识别的 token ID  
**依赖**: `lexer.py` (TokenType), `xgrammar` (TokenizerInfo, VocabType)

#### 核心映射: TOKEN_TYPE_TO_VOCAB (dict)

```
TokenType.KW_FUNC  → "FUNC"       (关键字)
TokenType.IDENTIFIER → "IDENT"    (标识符占位)
TokenType.INTEGER_LITERAL → "INT_LIT"  (字面量占位)
TokenType.OP_EQ    → "EQ"         (运算符)
TokenType.LPAREN   → "LPAREN"     (分隔符)
...
```

**设计要点**: GBNF 语法文件里引用的 token 名（如 `"FUNC"`、`"IDENT"`）必须与这里的 vocab string 完全一致。

#### 公共 API

```python
TOKENIZER_INFO       # TokenizerInfo 实例, 传给 GrammarCompiler
TOKEN_ID_MAP         # dict[TokenType, int], 直接查 token ID
VOCAB_SIZE           # 111
get_token_id(tt)     # TokenType → int (找不到回退到 IDENT)
get_token_name(tt)   # TokenType → str (如 "FUNC")
```

#### build_vocab_list() 排序规则

```
顺序: 关键字 → 标识符占位 → 字面量占位 → 运算符 → 分隔符 → 空白 → 特殊
```

这个顺序决定 token ID，必须与 GBNF 文件中使用的 token 名称完全对应。

### 3.3 cangjie_token.gbnf — Token 级语法规则

**文件**: `grammar/cangjie_token.gbnf` (269 行)  
**职责**: 用 EBNF 描述仓颉所有合法 token 排列方式  
**依赖**: XGrammar 的 GrammarCompiler 编译此文件

#### 结构分层

```
第1层: Token 占位符 (15-21行)
  定义 any_ident, literal 等基本 token 组合

第2层: 类型表达式 (26-44行)
  type_name → array_type → func_type → nullable_type → tuple_type → type

第3层: 表达式 (50-111行) — 按运算符优先级链式下降
  primary → postfix_expr → unary_expr → multiplicative_expr
  → additive_expr → shift_expr → range_expr → comparison_expr
  → type_check_expr → equality_expr → bitwise_and/or/xor_expr
  → logical_and/or_expr → coalescing_expr → pipeline_expr
  → assignment_expr → expression

第4层: 语句 (117-179行)
  var_decl | assign_stmt | if_stmt | while_stmt | for_stmt | ...
  → statement → statements

第5层: 声明 (185-249行)
  func_decl | main_decl | class_decl | struct_decl | enum_decl | ...
  → declaration

第6层: 程序结构 (255-269行)
  package_decl | import_decl | declaration
  → top_level_item → root
```

#### 表达式优先级链 (从低到高)

```
赋值:       =, +=, -=, *=, ...
管道:       |>, ~>
空合并:     ??
逻辑或:     ||
逻辑与:     &&
位或:       |
位异或:     ^
位与:       &
相等:       ==, !=
类型检查:   is, as
比较:       <, >, <=, >=
范围:       .., ..=
移位:       <<, >>
加减:       +, -
乘除:       *, /, %, **
一元:       -, !, ++, --
后缀:       .ident, (args), [idx], !, {fields}
原始:       literal, ident, (expr), this, super, [...], lambda
```

### 3.4 syntax_checker.py — 语法+语义统一调度

**文件**: `src/syntax_checker.py` (272 行)  
**职责**: 协调 lexer → 语法检查 → 语义检查的完整流程  
**依赖**: `lexer.py`, `token_vocab.py`, `semantic_checker.py`, `xgrammar`

#### 核心类: CheckResult

```python
@dataclass
class CheckResult:
    tokens: List[str]           # 成功检查的 token 文本列表
    syntax_results: List[int]   # 语法结果 (1/0)
    semantic_results: List[int] # 语义结果 (1/0)
    passed: bool                # 全部通过?
    error_token: Optional[str]  # 第一个出错的 token
    error_line: Optional[int]   # 出错行号
    error_col: Optional[int]    # 出错列号
    error_type: str             # "syntax" / "semantic" / ""
    error_message: str          # 错误描述

    format_output() → str       # 格式化输出:
      token: var x = 42
      语法: 1, 1, 1, 1
      语义: 1, 1, 1, 1
```

#### 核心类: CangjieSyntaxChecker

```
CangjieSyntaxChecker
├── __init__(grammar_path)
│   ├── 加载 cangjie_token.gbnf
│   ├── GrammarCompiler(TOKENIZER_INFO) → 编译语法
│   └── 保存 _compiled_grammar
│
├── check_token_by_token(code) → CheckResult
│   ├── _preprocess_comments(code)        # 去掉注释
│   ├── CangjieLexer → tokenize()         # 分词
│   ├── 过滤空白 token (WS, NEWLINE, COMMENT, UNKNOWN)
│   ├── 创建 GrammarMatcher + SemanticChecker
│   ├── for 每个有效 token:
│   │   ├── token_id = get_token_id(token.type)
│   │   ├── matcher.accept_token(token_id)        # XGrammar O(1)
│   │   ├── _token_invalid_in_kw_context(...)      # 辅助检查
│   │   ├── semantic.process(token)                # 语义检查
│   │   └── 任一失败 → 立即返回 CheckResult (失败)
│   ├── semantic.finalize()                        # 末尾检查
│   └── 返回 CheckResult (成功)
│
├── _preprocess_comments(code) → str       # 静态方法
├── _token_invalid_in_kw_context(...) → bool
└── _valid_after_kw_ident(kw_type) → set   # 静态方法
```

#### 辅助语法检查: _token_invalid_in_kw_context

XGrammar 只知道 token 序列是否合法，不知道上下文语义。这个函数补充检查两类语法错误：

| 场景 | 示例 | 检测逻辑 |
|------|------|----------|
| Case A: 关键字后缺标识符 | `let +` | 前一个 token 是声明关键字 (var/let/func/class...), 当前 token 不是 IDENT → 报错 |
| Case B: 关键字+标识符后缺合法后继 | `let a +` | 前两个是 `关键字 IDENT`, 当前 token 不是 `:`/`=`/`;` → 报错 |

### 3.5 semantic_checker.py — 增量语义检查器

**文件**: `src/semantic_checker.py` (672 行，最复杂的模块)  
**职责**: token 级别的增量语义检查  
**依赖**: 仅 `lexer.py` (Token, TokenType)

#### 核心数据结构

##### ScopeStack — 栈式符号表

```
作用域栈模型:
  [全局作用域]          ← _stack[0] (dict), _tags[0]
  [func f 的作用域]     ← _stack[1] (dict), _tags[1] = "func"
  [if 块的作用域]       ← _stack[2] (dict), _tags[2] = "block"
  [while 循环的作用域]   ← _stack[3] (dict), _tags[3] = "loop"

操作:
  push(tag)    : 遇到 { → 在栈顶加一个空 dict
  pop()        : 遇到 } → 从栈顶弹掉一个 dict (保留全局作用域)
  declare(...) : 在当前 dict 里注册符号
  lookup(name) : 从栈顶往下查，找到第一个匹配的符号
  update_type(): 更新最近声明的符号类型 (用于类型推导)

属性:
  depth        : 当前嵌套深度
  in_loop      : 当前在几层循环内 (用于 break/continue 检查)
  in_func      : 当前在几层函数内 (用于 return 检查)
  in_class_body: 最内层是否是 class/struct 体
```

##### SemanticChecker 内部状态机

```python
class SemanticChecker:
    # 声明追踪
    _decl_kw: TokenType?      # 当前声明类型 (VAR/LET/FUNC/CLASS/...)
    _decl_name: str?          # 正在声明的名称
    _decl_type: str?          # 声明中标注的类型 ("Int32", "Float64"...)

    # 函数参数
    _pending_params: [(name, type?)]  # 待注册参数 (在 { 时才正式入符号表)
    _in_params: bool                  # 当前在括号内解析参数
    _expecting_param_name: bool       # 期望下一个 token 是参数名

    # 上下文标志
    _entering_loop: bool     # while/for → 下一对大括号是循环体
    _in_struct_init: bool    # Point { x: 0.0 } → 花括号是结构体初始化
    _pending_class_ident: str?  # class 体内遇到的未声明标识符 (可能是字段)
    _in_package_path: bool   # package 路径中, 不查符号表
    _in_import_path: bool    # import 路径中, 不查符号表

    # 类型追踪 (P1-2)
    _current_expr_type: str?   # 当前表达式的最新类型
    _expected_type: str?       # 期望的类型 (从 var x: Int32 = ... 中的 :Int32)
    _func_return_type: str?    # 当前函数的返回类型 (用于检查 return)

    # 前驱 token 追踪
    _prev_type: TokenType?
    _prev2_type: TokenType?

    # 全局计数
    _has_main: bool           # main() 已出现?
    _paren_depth: int         # 括号嵌套深度
```

#### process() 核心路由逻辑

```
process(token) 入口
  │
  ├─ STATEMENT_START? (var/if/while/return/}/...)
  │    └─ 先检查缓存的类型匹配, 再清空类型状态
  │
  ├─ LBRACE → _enter_brace()    ─── 推作用域, 注册参数, 判断标签
  ├─ RBRACE → _exit_brace()     ─── 弹作用域, 清除结构体初始化标志
  ├─ LPAREN → 括号深度+1, 可能进入参数模式
  ├─ RPAREN → 括号深度-1, 退出参数模式
  ├─ KW_PACKAGE / KW_IMPORT → 进入路径模式 (跳过符号查找)
  ├─ KW_VAR/KW_LET/KW_FUNC/... → _start_decl()
  ├─ KW_WHILE/KW_FOR/KW_DO → 打上 _entering_loop 标记
  ├─ IDENTIFIER → _handle_identifier() ─── 最复杂的分支 (见下)
  ├─ OP_ASSIGN (=) → 有类型注解时设置 _expected_type
  ├─ COLON (:) → class 体内触发字段注册
  ├─ COMMA (,) → 参数模式下重置, 准备接收下一个参数
  ├─ SEMICOLON (;) → 触发类型推导 + 赋值类型检查 + _end_decl()
  ├─ KW_BREAK → 检查 in_loop > 0
  ├─ KW_CONTINUE → 检查 in_loop > 0
  ├─ KW_RETURN → 检查 in_func > 0, 设置 _expected_type = _func_return_type
  ├─ 字面量 (INT/FLOAT/STR/TRUE/FALSE) → 设置 _current_expr_type
  └─ 其他 → 仅 _advance()
```

#### _handle_identifier() — 标识符最核心的分发逻辑

```
遇到一个 IDENTIFIER, 按优先级判断它是什么角色:

Case -1:  在 struct init 里 (Point { x: 0.0 })
          → 字段名, 不查符号表, 直接返回 OK

Case -1b: 在 package/import 路径里
          → 路径片段, 不查符号表

Case 0:   在函数的参数列表里, 且在等参数名
          → 这是参数名, 加入 _pending_params

Case 0b:  在参数列表里, 前一个是 COLON
          → 这是参数的类型注解, 更新 pending_params 的类型

Case 1:   有 _decl_kw 且还没有 _decl_name (如 var □ = ...)
          → 这是声明名, 调 _register_declaration()

Case 1b:  在 func 声明中, 前一个是 COLON, 不在参数列表里
          → 这是函数返回类型

Case 2:   在 var/let 声明中, 前一个是 COLON
          → 这是变量类型注解, 设置 _expected_type

Case 3:   for (□ ...) — 前一个是 KW_FOR+LPAREN
          → 这是 for 循环变量, 直接注册

Case 3b:  前一个是 DOT
          → 成员访问 obj.field, 不查符号表

Case 4:   在 class body 里, 没有 _decl_kw
          → 可能是字段名, 设置 _pending_class_ident

Case 5:   默认 — 表达式上下文
          → _lookup_identifier(): 查符号表 + 设置 _current_expr_type
```

#### 类型兼容性规则

```python
_are_types_compatible(expected, actual):
  expected == actual           → True   # 完全相同
  expected in FLOAT and actual in INT  → True  # 整数可自动转浮点
  both in INT                  → True   # 整数之间可互转
  both in FLOAT                → True   # 浮点之间可互转
  both Bool / both String      → True   # 同类可互转
  其他                         → False  # 不兼容!
```

### TokenType → Token → Token ID 转换链

```
源字符串                TokenType 枚举          Vocab 字符串        Token ID (整数)
──────────             ────────────            ────────────        ──────────────
"var"    ──lexer──→   KW_VAR          ──vocab──→  "VAR"      ──index──→  0
"x"      ──lexer──→   IDENTIFIER      ──vocab──→  "IDENT"    ──index──→  41
"="      ──lexer──→   OP_ASSIGN       ──vocab──→  "ASSIGN"   ──index──→  89
"42"     ──lexer──→   INTEGER_LITERAL ──vocab──→  "INT_LIT"  ──index──→  43

get_token_id(KW_VAR) → 0
```

### 语义状态随 Token 流转示例

```
代码: var x: Int64 = "hello";

Token         语义状态变化
─────         ──────────────────────────────────
var           _decl_kw = KW_VAR, _start_decl()
x             _register_declaration("x") → scope["x"] = {kind: variable}
:             _advance()

=             设置 _expected_type = "Int64" (保持)
"hello"       字面量 → _current_expr_type = "String"
;             触发 _check_assignment_type():
               expected("Int64") vs actual("String") → _are_types_compatible?
               → False → 返回 SemanticResult(ok=False, error="Type mismatch...")
```

## 5. 语法规则架构

### 为什么需要两套语法文件

| 文件 | 级别 | API | 速度 | 用途 |
|------|------|-----|------|------|
| `cangjie.gbnf` | 字符级 | `accept_string()` | 慢 (~0.5ms/char) | 旧方案, benchmark 中作为基线 |
| `cangjie_token.gbnf` | Token 级 | `accept_token()` | 快 (~26μs/token) | **主力方案** |

### Token 级语法的改造要点

字符级语法中:
```
func_decl ::= "func" ws_req any_identifier ws "(" ...
```
关键字是**字符串字面量**, 标识符是字符级正则规则。

Token 级语法中:
```
func_decl ::= "FUNC" any_ident "LPAREN" ...
```
关键字变成 **vocab token 名**, 标识符变成 `"IDENT"` token 占位符。

**关键**: XGrammar 将 `"FUNC"` 等 token 名与 `TokenizerInfo` 中的 vocab 名称匹配, 自动建立映射。

### 顶层规则调用链

```
root
└── top_level_item*
    ├── package_decl  : PACKAGE ident (. ident)* ;
    ├── import_decl   : IMPORT ident (. ident)* ;
    └── declaration   :
        ├── func_decl         : FUNC ident (params) (: type)? { body }
        ├── main_decl         : ident (params) { body }     ← 无 func 关键字
        ├── class_decl        : CLASS ident (: parents)? { members }
        ├── struct_decl       : STRUCT ident (: parents)? { fields }
        ├── enum_decl         : ENUM ident (: type)? { cases }
        ├── interface_decl    : INTERFACE ident (: parents)? { methods }
        ├── extend_decl       : EXTEND type (: parents)? { members }
        ├── operator_decl     : OPERATOR (op) (params) (: type)? { body }
        └── var_decl          : VAR/LET ident (: type)? (= expr)? ;
```

## 6. 类型系统

### 字面量默认类型

| 字面量 TokenType | 推导类型 |
|------------------|----------|
| `INTEGER_LITERAL` | `Int64` |
| `FLOAT_LITERAL` | `Float64` |
| `STRING_LITERAL` / `MULTILINE_STRING` | `String` |
| `RUNE_LITERAL` | `Rune` |
| `KW_TRUE` / `KW_FALSE` | `Bool` |

### 类型来源

| 来源 | 如何获取 | 示例 |
|------|----------|------|
| 字面量 | 查 `_LITERAL_TYPES` / `_BOOL_LITERAL_TYPES` | `42 → Int64` |
| 类型注解 | `: Type` 后紧跟的 IDENT | `: Int32` |
| 变量类型 | 从符号表查找 `sym.declared_type` | `x` 查表得 `Int32` |
| 函数返回类型 | 从符号表查找 `sym.declared_type` | `computeGcd(...)` 查表得 `Int64` |
| 类型推导 | `var x = <expr>` → 从 RHS 推断 | `var x = 42` → `Int64` |

### 运算结果类型 (未实现)

当前**不追踪**运算符的结果类型。意味着:
- `a > b` 不会推导为 `Bool`
- `a + b` 不会推导为 `Int64`/`Float64`

## 7. 已知局限与改进方向

详见 `SUMMARY_0520.md` 中的"已知问题与局限性"一章。主要六点:

1. **运算符结果类型不推导** — 可能漏检一些类型错误
2. **泛型类型仅限 type 位置** — `Array<T>()` 构造在表达式位置不工作
3. **隐式 main() 重复检测有 bug** — 无 func 关键字的 main 二次检测不生效
4. **函数调用实参不检查** — 传错类型的参数不会被发现
5. **类型检查偶尔依赖分号** — 无分号时 _expected_type 可能残留
6. **不支持嵌套函数** — 语法规则设计如此
