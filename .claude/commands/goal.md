# 目标：仓颉片段检查器迭代优化（56/100 → ≥90/100）

## 一句话结果
让官网隐藏用例通过数从 56/100 提升到 **≥90/100**，在保证输出正确的前提下压缩单用例耗时（≤5 秒硬上限，性能排名前五有加分），并完整留存每轮迭代记录。

## 背景
C++ 实现增量式语法+语义检查器（逐 token 读入，输出 0/1）。每轮迭代依赖用户手动上传官网评测：官网只返回**已通过**的用例名+耗时，未通过/超时的用例不会出现在结果里，因此缺失即失败；具体是报错还是超时，需要靠本地 100 个公开用例复现来区分。

## 每轮迭代流程（循环执行直到达标）
1. **总结改动**：用户带来新版本代码后，先列出本轮改了什么 —— 涉及文件、逻辑变更点、预期影响哪些用例类别。
2. **打包**：把源码（含 build.sh）压成 zip，命名 `cangjie-checker_v{N}_{YYYYMMDD}.zip`，并明确告诉用户上传。
3. **存档结果**：收到官网结果后写入 `results/results_{YYYYMMDD}_v{N}.md`（版本号、通过数、每个用例耗时表）。
4. **对比分析**：与上一轮对比 —— 新增通过/丢失通过的用例各是哪些；按类别（lambda、infer 泛型推断、容器 API err_*、字符串/数值转换等）统计分布变化。
5. **规划下一步**：把根因判断、候选优化方案（按预期收益排序）写进 `docs/iteration_notes.md`，等待用户反馈后进入下一轮。

## 约束
- **正确性优先**：输出必须逐 token 符合预期；输出 0 后用例立即终止，任何错位输出该用例 0 分。
- 每个版本的最终修改后，都必须保证本地 wrong/ wrong2/ 底下的100个公开样例无错判、无误报、无提前报，保证100/100正确性。
- 单用例总耗时 ≤5 秒；正确前提下压缩耗时争取性能分（前五名加分）。
- 版本号递增，zip 包与 results 记录一一对应、可追溯。
- zip包大小一定不能超过1MB。
- 分析以**用例类别**为单位，不针对单个用例名。
- 性能调优时参考 `performance-optimization` skill 的方法论，但主要杠杆在算法：增量解析、类型可达性预计算、缓存、避免重复工作。

## 完成标准
- 隐藏用例通过数 ≥ 90/100；
- `results/` 与 `docs/iteration_notes.md` 完整覆盖每一轮；
- 每个交付的 zip 可编译（build.sh → solution）。

## 反目标
- 不为提速牺牲正确性（WA 该用例 0 分，得不偿失）；
- 不针对用例名硬编码特判 —— 决赛会追加 100 个基于 context_final 的新用例，特判必然失效；
- 不修改评测协议（stdin 逐 token 输入 → stdout 0/1）；
- 不在没有本地复现或评测证据的情况下凭猜测定根因。
